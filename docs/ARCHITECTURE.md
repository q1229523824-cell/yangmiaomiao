# 架构说明

## 目标

该小程序采用“离线优先、确定性计算、快照驱动”的结构。核心业务不依赖后端、网络或大模型，优先保证禁忌不会失效、菜单不会意外刷新、营养和购物数据可以追溯到同一份计划。

## 模块边界

```text
原生页面 pages/
      │ 用户事件 / 展示模型
      ▼
services/ ───────────── presentation/
      │ 应用用例                │ 格式化
      ▼                         ▼
domain/  ◄────────────── data/
      │ 纯函数与领域约束          本地食材和菜谱
      ▼
repositories/
      │ schemaVersion 包装
      ▼
微信 wx.getStorage / wx.setStorage
```

- `data/`：食材营养、菜谱、早餐模板和默认档案。
- `domain/`：领域类型、营养计算、偏好解析、硬约束过滤、菜单生成、计划校验和购物清单。
- `services/`：首次生成、明确重生成和历史恢复等应用级状态转换。
- `repositories/`：微信本地 Storage 适配、版本信封、校验、迁移和共享串行事务队列。
- `presentation/`：把不可变领域快照转换成页面可直接渲染的数据。
- `pages/`：负责输入、确认、忙碌与错误反馈，不复制营养或排餐算法。

## 核心数据流

```text
Profile[] + Preferences + date + seed
                  │
                  ▼
           generateDailyPlan
                  │
                  ▼
      一份共享的 DailyPlan 快照
       ├─ profilesSnapshot
       ├─ preferencesSnapshot
       ├─ meals + portionsByMemberId
       ├─ goalsByMemberId
       └─ nutritionByMemberId
                  │
          ┌───────┼────────┐
          ▼       ▼        ▼
        今日页   购物清单   历史恢复
```

每餐的菜谱和食材只选择一次；每个 `MealItem` 使用 `portionsByMemberId` 保存个人克数。因此不会出现界面写大米、某位成员营养却按另一种主食计算的问题。

份量调整把蛋白质和热量差额分散到午、晚两餐，不把全天差额集中到一份肉类或主食。生成完成后还会执行可用性门禁：蛋白质、干重主食和其他食材分别采用与其称重状态相符的单份上限，同时检查模板所得热量与计算目标是否差距过大。门禁描述的是这套小型离线菜谱库的表达能力，不是医学推荐值；超出能力时明确停止并提示核对档案，不返回看似精确的极端份量。

单个候选组合未满足份量或热量门禁，不一定表示整个食材库无解。`generateDailyPlan` 会沿同一确定性随机流最多尝试 `MAX_PLAN_GENERATION_ATTEMPTS`（当前为 64）个候选，返回首个合法快照；重试不递增外部 seed、生成计数或菜单 ID，也不放宽硬禁忌。输入档案错误、空候选池、结构校验失败等错误立即向上抛出，只有 `UnsupportedCombinationError` 可以换一个候选。全部候选耗尽后明确失败，调用方保留旧菜单；若这次操作修改了偏好，则保存新偏好并隐藏不满足新条件的旧菜单。

## 菜单生命周期

| 事件 | 是否改变当前菜单 | 行为 |
|---|---:|---|
| 首次运行且没有菜单 | 是 | 生成第一份快照并保存 |
| 再次打开或切换 Tab | 否 | 读取现有快照 |
| 日期跨天 | 否 | 显示旧日期提示，由用户决定 |
| 保存档案修改 | 否 | 标记待重算，保留旧快照 |
| 新偏好可生成合法菜单 | 是 | 明确重算并保存新快照 |
| 新禁忌导致无合法菜单 | 否 | 保存禁忌、隐藏不安全旧菜单并提示处理 |
| 点击换菜/按新设置重算 | 是 | 使用递增计数生成可复现新种子 |
| 确认恢复历史 | 是 | 使用历史快照并恢复普通偏好，合并保留当前过敏原；不生成新菜单 |

菜单历史按新到旧保存，去重后最多保留 60 份。历史恢复不会覆盖用户当前可编辑档案；历史计划继续用自身 `profilesSnapshot` 准确展示当时份量和营养。

## 偏好与安全约束

离线解析器把中文短句转换成结构化 `Preferences`：

- `excludedFoodIds`、`excludedFoodGroups`、`allergens` 和 `avoidWhey` 是排餐硬约束。
- `preferredFoodIds`、做法、口味和清淡晚餐是软偏好；找不到对应偏好菜谱时可以从仍满足硬约束的池中选择。
- 食材是否允许在菜谱、早餐、主食和加餐入口统一检查。
- 当硬约束使候选池为空时抛出结构化错误，不回退到被排除食材。
- 重复输入同一偏好时最终状态不变，页面不会重新生成菜单。
- 明确“过敏/不耐受”表述进入独立 `allergens` 硬约束；普通偏好重置和历史恢复都不能静默删除当前过敏原，解除必须使用明确取消表述。

解析器不是自然语言大模型。未识别或暂不支持的表达会反馈给用户，不应将模糊语言静默升级为医疗结论。

当前过敏原检查只覆盖食材目录中的结构化标记，不解析酱汁文字、品牌配料或交叉污染，因此产品不能承诺医学意义上的“无过敏原”。

## 本地持久化

新增外卖链路为 `Profile + Preferences → getTakeoutRecommendations → 营养区间与匹配/未匹配结果 → takeout 页面`。`data/takeout-catalog.ts` 是明确标注份量假设的本地点单组合；`domain/takeout.ts` 负责热量/蛋白门槛与主食材、潜在调料禁忌检查。它不依赖 `DailyPlan` 是否已经生成，也不把估算区间转换成该快照的精确值。

`AppState.takeout` 单独保存收藏和按日期/成员/午晚餐索引的参考记录。`services/takeout-state.ts` 只做不可变状态转换，通过同一仓库事务写入；页面在事务内用最新档案、偏好重新筛选，拒绝失效卡片事件。普通打开不写入，旧参考与新条件不符时提示重新选择并允许移除；跨午夜选择会先刷新日期，清除则针对点击时展示的记录日期。

schema 3 的迁移为 v2 原数据追加空外卖字段；v1 同时走既有刷新标记迁移。当前版本外卖字段损坏会停止加载；旧存储和剪贴板备份复用同一迁移路径。外卖数据随完整备份导出、恢复和清除。

当前应用数据保存在命名空间键 `fitness-couple:app-state` 中，信封包含：

```text
schemaVersion + savedAt + AppState
```

`AppState` 包含档案、偏好、当前菜单、历史、生成计数和每份菜单的购物勾选。读取时验证嵌套结构和 `DailyPlan` 不变量；旧 schema 可显式迁移，只有真正缺失的键才使用默认状态。损坏、未来版本或迁移失败的数据会保留原缓存、停止写入并抛出可识别错误，由档案页提供用户确认后的清除重建入口。存储 API 的真实失败会继续抛出并由页面展示，不能被当成“首次运行”覆盖。

四个页面取得同一个仓库实例，`load`、`update`、`transaction` 和清除操作进入共享 Promise 队列。`update`/`transaction` 在队列中读取最新状态、计算本次变更并保存，再将提交后的快照交给页面，避免拿旧状态整份覆盖另一个页面刚保存的修改。档案只更新档案及重算标记，购物勾选绑定点击时的菜单 ID，历史恢复在提交时重新检查最新过敏原记录。

事务回调返回原状态对象表示无变更，不重复写入或刷新 `savedAt`。一次失败不会使队列永久拒绝后续操作，页面只在成功提交后更新已保存状态；回调内只计算状态，不可再次调用同一仓库的排队方法，以免等待自身。这里的事务保证同一小程序运行实例内的顺序，不提供跨设备事务或云同步。

“清除本地数据”仅删除本应用命名空间下的键，并与其他操作串行执行。仓库使用重置版本计数拒绝清除前发起、却排到清除之后的旧写入，避免刚删除的数据被迟到操作写回。

## 原生手机交互

保留“今日、购物、档案、历史”四个原生 Tab。首页明确首次预填档案是示例并提供档案入口；档案页固定底部保存栏，页面留出底部空间，数字输入设置对应键盘和避让距离。校验失败会标红并滚至首个有错误的成员，暂时切换 Tab 不丢失未保存草稿。

主要操作有忙碌、禁用和失败反馈，长称呼、菜名和食材列可以在窄屏换行。保存档案后仍保留旧菜单，用户回到今日页主动重算。页底简要说明首次获取/更新代码包需要联网、业务数据保存在本机和两台手机不自动同步；开发者工具模拟器交互已由自动化回归覆盖，手机键盘、触控和飞行模式仍需真机验收。

## 离线与信任边界

运行时代码没有 `wx.request`、上传、下载、WebSocket、浏览器 DOM 或第三方 SDK。小程序代码包已经到达设备后，核心流程仅依赖打包数据和微信本地 Storage。

首次下载、更新、微信开发者工具登录、体验版上传和平台审核仍需要网络。当前没有账号、云备份或自动跨设备同步；档案页的备份是用户主动复制的本地剪贴板文本。

本地备份使用显式格式标记、当前 schema 版本和完整 `AppState` 快照。导入流程先限制文本大小，再解析 JSON、拒绝未知格式/未来版本并复用状态校验与 v1 迁移逻辑，最后在共享存储队列中显式替换状态；它不先读取旧 envelope，因此即使旧缓存损坏也能恢复。解析或用户取消确认都不会写入存储。

开发者工具 `preview` 的预览码与公众平台体验版二维码属于不同访问入口。体验成员通过 `upload` 后在公众平台选为体验版本的代码进入，页面路径为 `pages/index/index`，扫码账号需有“查看体验版”权限；仅有该权限不能用开发版预览码代替。体验版不代表已提交审核或正式发布。

## 验证策略

- 领域测试：营养、用户可达边界档案、排餐确定性、正常成人跨种子份量和极端目标拒绝。
- 候选恢复测试：份量不匹配后的确定性继续选择、重试上限、种子/菜单 ID 稳定及非可恢复错误即时抛出。
- 随机种子回归：跨大量种子证明番茄、鱼类等硬排除不会泄漏。
- 生命周期测试：首次生成、重开、跨日期、档案修改和明确重算。
- 存储测试：版本往返、迁移、损坏数据保全、未来 schema 拒绝、真实错误透传、跨页面并发修改不丢失、失败后重试、无变更不写入及清除后旧写入失效。
- 展示/历史测试：最多 60 份、三餐与双人热量、恢复偏好；页面控制器覆盖冷启动、跨页面持久化和恢复入口。
- 安全回归测试：六种已建模过敏原的 64 种组合跨 32 个种子均不生成目录冲突，并验证有过敏原记录时不展示调味建议。
- 静态结构测试：所有声明页面文件齐全，无浏览器 DOM、网络 API、云调用、远程运行时 URL 和常见前端秘密。
- 平台模板检查：`npm run verify:wechat` 调用微信开发者工具的官方 `wcc/wcsc`。
- 原生模拟器回归：`npm run verify:simulator` 在已登录、有 AppID 权限且启用 CLI 服务的开发者工具中执行。脚本核对 AppID 和 `devtools` 环境后，备份项目存储键、注入测试数据并执行页面流程，退出处理恢复该键的原值并验证恢复；不清空其他存储键。2026-09-08 已完成 16 项检查并捕获 0 个应用异常。
- 模拟器报告、截图和私有备份写入被 Git 忽略的 `artifacts/simulator/<运行时间>/`。`storage-backup.private.json` 可能包含使用者资料；异常中断或 `restored: false` 时需保留备份并核对恢复，不能把测试数据当成原有档案。
- 模拟器通过故障注入拒绝网络 API 并检查调用次数，验证的是业务 API 独立性；iOS/Android 下载代码包后的飞行模式、键盘和触控流程仍需真机记录。

上述内容描述验证范围和执行入口，不表示每个层级已经通过。实际命令结果、截图、存储恢复状态和对应代码版本记录在 [PROGRESS.md](../PROGRESS.md) 及 [RELEASE_CHECKLIST.md](../RELEASE_CHECKLIST.md)，模拟器脚本提供逐项 `report.json`。
