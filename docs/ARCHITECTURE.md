# 架构说明

## 目标

该小程序采用“离线优先、确定性计算、快照驱动”的结构。核心业务不依赖后端、网络或大模型，优先保证禁忌不会失效、菜单不会意外刷新、营养和购物数据可以追溯到同一份计划。

## 模块边界

```text
原生页面 pages/
      │ 用户事件 / 展示模型
      ▼
services/ ───────────── presentation/
      │ 应用用例                │ 格式化
      ▼                         ▼
domain/  ◄────────────── data/
      │ 纯函数与领域约束          本地食材和菜谱
      ▼
repositories/
      │ schemaVersion 包装
      ▼
微信 wx.getStorage / wx.setStorage
```

- `data/`：食材营养、菜谱、早餐模板和默认档案。
- `domain/`：领域类型、营养计算、偏好解析、硬约束过滤、菜单生成、计划校验和购物清单。
- `services/`：首次生成、明确重生成和历史恢复等应用级状态转换。
- `repositories/`：微信本地 Storage 适配、版本信封、校验和迁移。
- `presentation/`：把不可变领域快照转换成页面可直接渲染的数据。
- `pages/`：负责输入、确认、忙碌与错误反馈，不复制营养或排餐算法。

## 核心数据流

```text
Profile[] + Preferences + date + seed
                  │
                  ▼
           generateDailyPlan
                  │
                  ▼
      一份共享的 DailyPlan 快照
       ├─ profilesSnapshot
       ├─ preferencesSnapshot
       ├─ meals + portionsByMemberId
       ├─ goalsByMemberId
       └─ nutritionByMemberId
                  │
          ┌───────┼────────┐
          ▼       ▼        ▼
        今日页   购物清单   历史恢复
```

每餐的菜谱和食材只选择一次；每个 `MealItem` 使用 `portionsByMemberId` 保存个人克数。因此不会出现界面写大米、某位成员营养却按另一种主食计算的问题。

## 菜单生命周期

| 事件 | 是否改变当前菜单 | 行为 |
|---|---:|---|
| 首次运行且没有菜单 | 是 | 生成第一份快照并保存 |
| 再次打开或切换 Tab | 否 | 读取现有快照 |
| 日期跨天 | 否 | 显示旧日期提示，由用户决定 |
| 保存档案修改 | 否 | 标记待重算，保留旧快照 |
| 新偏好可生成合法菜单 | 是 | 明确重算并保存新快照 |
| 新禁忌导致无合法菜单 | 否 | 保存禁忌、隐藏不安全旧菜单并提示处理 |
| 点击换菜/按新设置重算 | 是 | 使用递增计数生成可复现新种子 |
| 确认恢复历史 | 是 | 使用历史快照并恢复普通偏好，合并保留当前过敏原；不生成新菜单 |

菜单历史按新到旧保存，去重后最多保留 60 份。历史恢复不会覆盖用户当前可编辑档案；历史计划继续用自身 `profilesSnapshot` 准确展示当时份量和营养。

## 偏好与安全约束

离线解析器把中文短句转换成结构化 `Preferences`：

- `excludedFoodIds`、`excludedFoodGroups`、`allergens` 和 `avoidWhey` 是排餐硬约束。
- `preferredFoodIds`、做法、口味和清淡晚餐是软偏好；找不到对应偏好菜谱时可以从仍满足硬约束的池中选择。
- 食材是否允许在菜谱、早餐、主食和加餐入口统一检查。
- 当硬约束使候选池为空时抛出结构化错误，不回退到被排除食材。
- 重复输入同一偏好时最终状态不变，页面不会重新生成菜单。
- 明确“过敏/不耐受”表述进入独立 `allergens` 硬约束；普通偏好重置和历史恢复都不能静默删除当前过敏原，解除必须使用明确取消表述。

解析器不是自然语言大模型。未识别或暂不支持的表达会反馈给用户，不应将模糊语言静默升级为医疗结论。

当前过敏原检查只覆盖食材目录中的结构化标记，不解析酱汁文字、品牌配料或交叉污染，因此产品不能承诺医学意义上的“无过敏原”。

## 本地持久化

当前应用数据保存在命名空间键 `fitness-couple:app-state` 中，信封包含：

```text
schemaVersion + savedAt + AppState
```

`AppState` 包含档案、偏好、当前菜单、历史、生成计数和每份菜单的购物勾选。读取时验证嵌套结构和 `DailyPlan` 不变量；旧 schema 可显式迁移，损坏或未来版本数据安全回退。存储 API 的真实失败会继续抛出并由页面展示，不能被当成“首次运行”覆盖。

“清除本地数据”仅删除本应用命名空间下的键。

## 离线与信任边界

运行时代码没有 `wx.request`、上传、下载、WebSocket、浏览器 DOM 或第三方 SDK。小程序代码包已经到达设备后，核心流程仅依赖打包数据和微信本地 Storage。

首次下载、更新、微信开发者工具登录、体验版上传和平台审核仍需要网络。当前没有账号、云备份或跨设备同步。

## 验证策略

- 领域测试：营养、边界档案、排餐确定性和份量有效性。
- 随机种子回归：跨大量种子证明番茄、鱼类等硬排除不会泄漏。
- 生命周期测试：首次生成、重开、跨日期、档案修改和明确重算。
- 存储测试：版本往返、迁移、损坏回退、真实错误透传和命名空间清除。
- 展示/历史测试：最多 60 份、三餐与双人热量、恢复偏好。
- 静态结构测试：所有声明页面文件齐全，无网络 API 和常见前端秘密。
- 平台模板证据：微信开发者工具 `2.02.2608060` 的官方 `wcc/wcsc` 已通过 4 个 WXML 和 5 个 WXSS。
- 待补平台证据：真实 AppID 下的完整项目编译、登录态模拟器和 iOS/Android 断网真机流程。
